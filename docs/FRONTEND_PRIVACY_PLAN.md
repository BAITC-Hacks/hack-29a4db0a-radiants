# План frontend: приватность, роли и объяснимое развитие

> Статус 2026-09-23: экран доступа, переход после импорта, русский интерфейс и перепроверка сессии реализованы в `feat/private-frontend`. Этот документ сохраняет исходный план; актуальные результаты и ограничения проверки — в [FRONTEND_PRIVATE_UI.md](FRONTEND_PRIVATE_UI.md).

## 1. Цель и границы

Сотрудник входит в личный аккаунт и видит собственный профиль. HR входит в отдельный аккаунт, видит разрешённые профили, аналитику и импорт. Участие других сотрудников не открывается сотруднику ни в интерфейсе, ни через API. Карьерные рекомендации добровольны; HR не может нажать «завершить» за сотрудника.

Это локальная аутентификация для воспроизводимого MVP. Корпоративные SSO, MFA, подразделения доступа, согласия на обмен с коллегами, восстановление пароля и управление жизненным циклом аккаунта — отдельные последующие задачи. Не показывать элементы этих функций как работающие до появления backend.

Основной запуск остаётся `docker compose up --build`. Данные и аккаунты сохраняются в SQLite volume. Для внутреннего размещения оператор ограничивает сетевой доступ и настраивает HTTPS/`APP_ORIGIN`; сам факт использования Docker не превращает публичную машину во внутренний контур.

## 2. Что уже реализовано в этой ветке

- `AuthBoundary` проверяет сессию до монтирования `App`. Пока ответа нет, показывается только загрузка; ошибка проверки не открывает данные.
- Форма входа имеет username/password, состояния загрузки/ошибки, стандартные autocomplete и не содержит общего пароля или кнопки выбора роли.
- `session`, CSRF и данные профиля хранятся только в памяти React. Нет localStorage, sessionStorage, JWT в URL или клиентской копии session cookie.
- `App` получает подтверждённые сервером `session` и `api`. Сотруднику заранее выбран `session.user.employeeId`; нет переключателя сотрудников, HR и импорта.
- HR видит переключатель сотрудников, HR dashboard и импорт, но не кнопку завершения активности.
- Любой API `401`, истечение `expiresAt` и выход отменяют запросы текущей сессии и убирают защищённый `App`. Новый вход создаёт новый экземпляр приложения без данных предыдущего пользователя.
- Запросы используют `credentials: "same-origin"` и `cache: "no-store"`. Все mutation POST через `createCareerApi` получают `X-CSRF-Token`.
- При ошибке выхода профиль сразу скрыт. Интерфейс предлагает повторить выход, не утверждает, что серверная сессия удалена.
- Проверка сессии, login и logout ограничены 10 секундами и отменяют HTTP-запрос при таймауте. Истечение сессии снимает состояние неудачного logout и возвращает форму входа.
- AI загружается отдельно от профиля и completion. Кнопка повторного AI-запроса сохраняет проверку соответствия результата исходному профилю.
- Пустые рекомендации показывают серверную причину и раскрываемый список исключённых мероприятий с причинами.
- Формула readiness берётся из `recommendationDiagnostics.readinessExplanation`; frontend её не рассчитывает.
- Видна полная история, включая статусы, даты и `assigned_by`; обязательные активности сохраняют отдельный блок и сроки.

Оформление новых экранов можно улучшать, сохраняя эти правила. Не заменять текущий `App` старой версией из ветки frontend.

## 3. Канонические контракты

Источник типов: `src/contracts/auth.ts`, `src/contracts/api.ts`, `src/types/career.ts`. Не создавать второй набор domain DTO.

```ts
type UserRole = "employee" | "hr";
interface AuthSession {
  user: {
    id: string;
    username: string;
    role: UserRole;
    employeeId: string | null;
  };
  expiresAt: string; // ISO timestamp, реальное время срока сессии
  csrfToken: string;
}
```

`employeeId` обязателен для employee, `null` для HR. Роль задаёт сервер. Не выводить права из имени пользователя, email, выбранного профиля или department.

```json
{ "data": {} }
```

```json
{ "error": { "code": "FORBIDDEN", "message": "Readable message", "details": [] } }
```

Профиль и рекомендации остаются `{ data: EmployeeDetail }`; completion возвращает `{ data: { activity, view, progress } }`. `explanationSource` сохраняется: `llm` либо `fallback`.

## 4. API входа и сессии

| Запрос | Тело/заголовки | Результат |
| --- | --- | --- |
| `GET /api/auth/session` | Cookie браузера | `200 { data: AuthSession }` либо `401 AUTH_REQUIRED` |
| `POST /api/auth/login` | JSON `{ username, password }`; браузерный `Origin` | `200 { data: AuthSession }`, сервер устанавливает HttpOnly `cq_session` |
| `POST /api/auth/logout` | `X-CSRF-Token`, Cookie, `Origin` | `200 { data: { signedOut: true } }`, сервер удаляет сессию/cookie |

Все запросы относительные `/api/...`. Для login используется `Content-Type: application/json`; для FormData импорта вручную Content-Type не задавать. `Origin` выставляет браузер: не пытаться подделывать его в JavaScript. API на другом домене сейчас не поддерживается схемой same-origin.

Session cookie — HttpOnly/SameSite=Strict; при HTTPS origin сервер ставит Secure. В JavaScript cookie не читать и не копировать. CSRF брать только из ответа session/login и использовать лишь для текущей сессии.

`expiresAt` относится к реальному времени сессии, а бизнес-логика каталога сохраняет snapshot `2026-10-01`. Эти две даты нельзя смешивать.

## 5. Матрица разрешений

| Действие | Гость | Сотрудник | HR |
| --- | --- | --- | --- |
| Страница входа, `/api/health` | Да | Да | Да |
| Каталог событий/навыков | Нет | Да | Да |
| Список сотрудников | Нет | Только своя карточка | Все доступные карточки |
| Профиль, рекомендации, история | Нет | Только свой employeeId | Разрешённые профили |
| Completion | Нет | Только себе | Нет |
| HR summary | Нет | Нет | Да |
| Импорт JSON/CSV | Нет | Нет | Да |
| Список/создание аккаунтов | Нет | Нет | Да |

Frontend ограничивает интерфейс для понятного UX. Безопасность обеспечивают backend guards на каждом endpoint. Любой ручной запрос к чужому employeeId должен быть отклонён сервером.

Публичные рейтинги, поиск чужих профилей сотрудником и сравнение личной вовлечённости не добавлять. Согласие на открытие данных коллегам в MVP не реализовано, поэтому такого доступа нет вообще.

## 6. Ошибки и переходы

| Код/статус | Реакция frontend |
| --- | --- |
| `401 AUTH_REQUIRED` на protected API | Отменить запросы, размонтировать App/очистить данные, показать вход |
| `401 INVALID_CREDENTIALS` на login | Оставить форму, показать нейтральную ошибку; не раскрывать существование username |
| `403 FORBIDDEN` | Сообщить об отсутствии права; не разлогинивать и не повторять запрос автоматически |
| `403 CSRF_INVALID` | Не повторять mutation; предложить обновить сессию/страницу и повторить вручную |
| `403 ORIGIN_FORBIDDEN` | Не обходить защиту; оператор проверяет URL и `APP_ORIGIN` |
| `429 LOGIN_RATE_LIMITED` | Показать серверное сообщение об ожидании; не запускать автоматические повторы |
| `400/422 VALIDATION_ERROR` | Подсветить файл/строку/поле по `error.details`; сохранить введённые несекретные поля |
| `409 USERNAME_EXISTS` | Предложить другое имя пользователя |
| `422 EMPLOYEE_NOT_FOUND` при создании аккаунта | Сначала импортировать/выбрать существующий профиль |
| `409` на completion | Активность уже завершена; обновить профиль чтением, не повторять POST |
| Timeout/сеть после mutation | Результат неизвестен; обновить профиль перед повтором, исключить двойное завершение |

`ApiError` сохраняет status/code. UI никогда не выводит сырой stack trace, cookies, пароли или `.env`.

## 7. Аккаунты: backend готов, UI — следующая задача frontend

При первом запуске сервер создаёт несколько стартовых аккаунтов со случайными паролями. Оператор получает их из `.data/initial-access.json` внутри своего SQLite volume. Этот файл не отдаётся HTTP API, не попадает в Git и не встраивается в страницу. Точные команды получения стартового доступа находятся в README.

**Порядок для нового профиля жюри:**

1. Войти в HR.
2. Импортировать JSON сотрудника; затем CSV его истории.
3. Создать персональный аккаунт, связанный с employeeId импортированного профиля.
4. Передать данные входа конкретному сотруднику/жюри приватно.
5. Выйти из HR и войти созданным employee для добровольного completion.

### Контракт управления аккаунтами

- `GET /api/hr/accounts` → `{ data: { items: Array<SessionUser & { active: boolean }> } }`. Паролей в ответе нет.
- `POST /api/hr/accounts` → тело `{ username, password, employeeId }`; `X-CSRF-Token` обязателен.
- Успех создания: `201 { data: SessionUser }`.
- Создаётся только роль employee. Не отправлять `role`; backend её не принимает.
- Username: 3–80 символов из `[a-zA-Z0-9_.-]`, нормализуется в нижний регистр.
- Новый пароль: 12–128 символов. Не обрезать пароль, не логировать, не хранить после ответа.
- employeeId должен существовать; роль/имя сотрудника показывать рядом, чтобы HR подтвердил правильную привязку.
- Изменение роли, сброс пароля, блокировка/разблокировка и удаление аккаунта не представлены endpoint: не делать фиктивных кнопок.

### Задачи для frontend

1. Добавить HR-only экран/диалог «Доступ сотрудников».
2. Добавить методы `getAccounts`/`createEmployeeAccount` в транспортный слой; использовать общий session signal, `onUnauthorized` и CSRF, не отдельный незащищённый fetch.
3. Список: username, employeeId, связанное имя сотрудника, active. Никаких паролей в таблице или DOM после создания.
4. Форма: выбор существующего сотрудника, username, password, подтверждение правильной привязки; без выбора роли.
5. При успехе очистить пароль и обновить список чтением. При timeout сначала прочитать список: запрос создания мог уже завершиться.
6. Добавить ссылку «Создать доступ» после успешного JSON-импорта с предвыбранным employeeId; CSV можно импортировать до или после создания аккаунта.
7. Показывать понятную инструкцию о приватной передаче пароля. Автоматическую отправку email не добавлять.

## 8. Защита от старых данных и переключения аккаунта

Для всех запросов нужен общий жизненный цикл сессии. В дополнение к отмене по employeeId контроллер AuthBoundary отменяет запросы списка, профиля, AI, HR, импорта и completion при выходе/401.

Обязательные сценарии:

- A вышел, B вошёл: данные A не появляются даже на один кадр и после позднего HTTP-ответа.
- AI ответа на старый профиль не меняет новый профиль.
- Completion/импорт обновили того же employee: старый AI ответ также отбрасывается.
- Переход Employee → HR, открытие импорта, logout отменяют старый AI запрос.
- Отменённый запрос старой сессии с поздним `401` не разлогинивает новую сессию.
- Ошибка logout скрывает данные сразу; нельзя сообщать «вышли» до подтверждения сервера.

Не вводить глобальный кэш профилей, service worker для private API или сохранение в localStorage. Если позже появится query library, namespace должен включать id сессии/пользователя, а logout обязан очищать весь private cache.

Для следующего усиления UX: перепроверять session после возврата вкладки в фокус/восстановления из bfcache, не сохраняя старые данные при обнаружении смены пользователя. Межвкладочный сигнал выхода можно реализовать без передачи секретов через BroadcastChannel; сервер всё равно остаётся источником прав.

## 9. Explainability и добровольность

### Карточка рекомендации

- Название, score, причины и historySignal брать из backend.
- Показать `before → after`, required и critical. `required === 0` означает «не требуется для цели», а не «0 required».
- Навыки подписывать названиями каталога; ID использовать как технический fallback при недоступном каталоге.
- Только `explanationSource === "llm"` с непустым `aiExplanation` даёт метку AI. Иначе показывать `deterministicExplanation` как правило/расчёт.
- AI не выбирает новые eventId и не изменяет прогресс. При несовпадении снимка профиля ответ игнорируется.

### Пустой блок рекомендаций

Использовать `EmployeeDetail.recommendationDiagnostics`: status, summary, blockedEvents. Не придумывать причины на frontend и не делать неподходящее мероприятие рекомендацией ради заполнения блока.

В диагностике предусмотрены `available`, `needs_career_goal`, `target_reached`, `no_eligible_events`; исключения: mandatory, audience, prerequisites, unavailable, completed, in_progress, no_gap_reduction. Счётчики событий описывают первую неуспешную проверку и не означают число сотрудников.

### Readiness

Показывать серверное число с одним десятичным знаком при необходимости. Изменение — в процентных пунктах. Формулу выводить из backend diagnostics; не пересчитывать её по таблице браузера. При отсутствии цели объяснение должно отражать отсутствие цели, а не обещать продвижение.

### Добровольность

Надпись: рекомендации — возможные шаги развития. Нет автоматической записи на курсы, штрафа за игнорирование, сравнительного рейтинга или возможности HR завершить шаг за сотрудника. Обязательные compliance/onboarding отображаются отдельно и не подмешиваются в карьерные рекомендации.

## 11. Этапы работы frontend

1. **Синхронизация:** обновиться от проверенного main; прочитать этот файл, API-контракты и README; не заменять auth scaffold.
2. **Аккаунты:** реализовать раздел 7 с ошибками/валидацией. Это главная оставшаяся функциональная задача.
3. **UX состояний:** улучшить подписи доступа/ошибок, фокус на login/403, читабельность diagnostics и адаптивность таблиц. Сохранять англоязычный интерфейс или локализовать весь экран последовательно.
4. **Сессии во вкладках:** session check при возврате фокуса и безопасное уведомление выхода между вкладками, без секретов в сообщениях.
5. **Интерактивные проверки:** проверить полный путь на реальном Docker API, затем оформить небольшой PR с описанием и результатами.

Владение: frontend — компоненты, hooks, клиентский транспорт и стили. Backend — сервер, guards, DTO и миграции. Изменение публичного контракта/зависимостей сначала согласовать с владельцем backend.

## 12. Критерии приёмки

### Вход и права

- Гость не видит имён/профилей/HR данных; API возвращает 401.
- Неверный пароль даёт нейтральную ошибку; ограничение попыток видно.
- Employee видит только свой employeeId; ручной запрос чужого id отклоняется.
- Employee не может вызвать HR, импорт или управление аккаунтами.
- HR видит аналитику и импорт, completion отсутствует в UI и возвращает 403 при прямом запросе.
- POST без правильных Origin/CSRF отклоняется без изменения базы.

### Полный сценарий

- HR: импорт JSON → CSV → создать доступ профилю.
- Выход → вход employee → профиль/история → причины рекомендации → completion → before/after/readiness/новая история.
- Повторное неповторяемое completion даёт 409; повторяемое EV_036 работает согласно бизнес-правилам.
- Выход → HR → статистика отражает изменение. Данные сохраняются после restart контейнера.
- Без ключа/при отключённом AI всё работает с честной меткой fallback.

### Регрессии интерфейса

- E0043: пустые рекомендации объясняются фактами backend, профиль не выглядит сломанным.
- Lead без цели: видны текущие навыки и причина отсутствия шага.
- Смена профиля/аккаунта во время AI не подмешивает старый результат.
- История показывает due date/assigned source и не теряет обязательные активности.
- Мобильный экран не обрезает форму, logout или таблицы без возможности прокрутки.

### Команды проверки

```bash
npm run typecheck
npm run lint
npm test
docker compose up --build
```

В PR перечислить выполненные browser-сценарии. Успешная компиляция сама по себе не доказывает разграничение доступа и корректную смену аккаунта.
