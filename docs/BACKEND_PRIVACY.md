# Backend: доступ и приватность

## Что реализовано

Серверная сессия обязательна. Единственные публичные API — health с агрегированными количествами и login. В обычном режиме сервер связывает сессию с индивидуальной учётной записью в SQLite; роль и employeeId из тела/заголовков клиента не принимаются. Начальный датасет синтетический. Опциональный режим общего демо-входа описан ниже: он сохраняет ограничения API по ролям, но не подтверждает личность сотрудника.

| Действие | Employee | HR | Без входа |
| --- | --- | --- | --- |
| Список сотрудников | Только собственная карточка | Все карточки | 401 |
| Профиль, история, рекомендации | Только собственный ID | Любой ID | 401 |
| Завершение активности | Только собственный ID | 403 | 401 |
| Каталог мероприятий/навыков | Да, без чужой истории | Да | 401 |
| HR-аналитика, импорт, аккаунты | 403 | Да | 401 |
| Health | Да | Да | Да |

Отсутствует возможность публиковать профиль коллегам: по умолчанию такой доступ закрыт. HR получает данные для своей служебной задачи. HR-доступ не означает согласие сотрудника на публичный рейтинг или распространение истории. Корпоративную политику доступа/хранения следует согласовать до загрузки реальных данных.

## Учётные записи и запуск

`docker compose up --build` применяет миграции SQLite, сохраняет бизнес-данные и генерирует три аккаунта только при отсутствии аккаунтов: `hr-admin`, `employee` → E0178, `employee2` → E0058. Если этих ID нет, используются первые доступные профили. Каждому генерируется случайный индивидуальный пароль. По умолчанию общий демо-вход выключен.

Оператор читает `docker compose exec app cat /app/.data/initial-access.json`. Для локальной разработки файл находится рядом с SQLite, по умолчанию `.data/initial-access.json`. На Linux файл создаётся с правами 0600; каталог/volume должен быть доступен только оператору. Файл не попадает в Git, Docker image, API или логи. После безопасной передачи персональных паролей его можно удалить; пока аккаунты существуют, он не генерируется заново. Потеря этого файла не должна решаться удалением рабочего volume: полноценное восстановление аккаунтов пока не реализовано.

Индивидуальные пароли хранятся как salted scrypt hashes (N=32768, r=8, p=3). Логин индивидуального аккаунта нормализуется в lowercase: 3–80 символов `[A-Za-z0-9_.-]`; новый пароль — 12–128 символов. HR создаёт аккаунт только для уже существующего сотрудника. В обычном режиме импорт профиля сам по себе не создаёт аккаунт и не даёт доступ.

## Общий вход для демонстрации

`DEMO_EMPLOYEE_LOGIN` по умолчанию `false`. Чтобы демонстратор мог открывать любой синтетический профиль, установить `DEMO_EMPLOYEE_LOGIN=true` в игнорируемом `.env` и пересоздать контейнер через `docker compose up --build`.

- Логин сотрудника — полное имя из датасета, пароль — **admin**. Поддерживаются пробелы и Unicode; поле входа принимает до 200 символов.
- Для тёзок добавить ID в скобках: `Ksenia Pavlova (E0058)`. Сервер выбирает соответствующий профиль; отдельного выбора роли на клиенте нет.
- Дополнительно импортированные сотрудники также получают демо-доступ при входе: создавать им индивидуальный аккаунт для этого сценария не требуется.
- HR входит как `hr-admin` со своим индивидуальным паролем. Общий пароль не даёт доступ к HR, импорту или управлению аккаунтами. Обычные пароли существующих аккаунтов не перезаписываются.
- На экране входа и после входа показана плашка **Demo mode — shared employee access, not private authentication.** Общий пароль позволяет открыть чужой синтетический профиль по имени, поэтому такой режим не обеспечивает приватность сотрудников и предназначен только для демонстрации.

Чтобы выключить общий вход, установить `DEMO_EMPLOYEE_LOGIN=false` и пересоздать контейнер. Общий пароль перестаёт приниматься, созданные через демо-вход сессии больше не допускаются к API. Индивидуальные учётные данные сохраняются. Новых HTTP-маршрутов или DTO этот режим не вводит: `POST /api/auth/login` продолжает принимать `{ username, password }`, где `username` в демо-сценарии содержит имя сотрудника.

Страница Next.js читает флаг при запросе на сервере, поэтому значение применяется в runtime после пересоздания контейнера. Для показа этого режима использовать основной Next.js/Compose интерфейс.

## HTTP-контракт

Типы: `src/contracts/auth.ts`. Все ответы сохраняют `{ data }` / `{ error: { code, message, details } }`.

```ts
interface AuthSession {
  user: { id: string; username: string; role: "employee" | "hr"; employeeId: string | null };
  expiresAt: string; // ISO UTC
  csrfToken: string;
}
```

- `POST /api/auth/login` — `{ username, password }`, ответ AuthSession и HttpOnly cookie.
- `GET /api/auth/session` — актуальная AuthSession или 401.
- `POST /api/auth/logout` — `{}`, ответ `{ signedOut: true }`, сессия удаляется из БД.
- `GET /api/hr/accounts` — `{ items: Array<SessionUser & { active: boolean }> }`, только HR, без хешей/паролей.
- `POST /api/hr/accounts` — строго `{ username, password, employeeId }`, ответ SessionUser, 201. Роль всегда employee; поле role отклоняется. Повторный логин — 409; неизвестный employeeId — 422.
- `PATCH /api/employees/:employeeId/career-goal` — только собственная цель сотрудника; строго `{ career_goal: { target_role, target_grade } | null }`. Пара role/grade проверяется по каталогу, возвращается пересчитанный EmployeeDetail. Текущие навыки, должность и права не изменяются. Контракт: [FRONTEND_COMPLETION_GOAL_HANDOFF.md](FRONTEND_COMPLETION_GOAL_HANDOFF.md).

Все POST и PATCH проверяют точное совпадение Origin с APP_ORIGIN; cross-site Fetch Metadata отклоняется. Все эти запросы, кроме login, также проверяют X-CSRF-Token из AuthSession. Клиент хранит CSRF только в памяти и отправляет cookie браузером. Поле Content-Type для FormData браузер формирует сам.

Cookie `cq_session`: случайный opaque token (256 бит), HttpOnly, SameSite=Strict, path=/; в БД только SHA-256 hash. Сессия действует 8 часов без автоматического продления. Logout отзывает текущую сессию. Пользователь с active=0 или истёкшая/несуществующая сессия немедленно получает 401. Каждое обращение сверяет текущую роль в БД. Secure включается при HTTPS APP_ORIGIN.

Ошибки: AUTH_REQUIRED/INVALID_CREDENTIALS 401, FORBIDDEN/CSRF_INVALID/ORIGIN_FORBIDDEN 403, LOGIN_RATE_LIMITED 429. После 5 неудачных входов для одного логина или 100 для всего приложения окно блокировки 15 минут от начала серии. Это ограничение локального MVP, а не распределённая защита от DDoS. JSON ограничен 64 KiB, multipart — 10 MiB; превышение 413. Приватные ответы и ошибки имеют private,no-store и Vary: Cookie. В аудит пишутся вход/выход, создание аккаунта, импорт и completion, без паролей или полной истории.

## Explainability и добровольность

EmployeeDetail дополнен `activityHistory` со всеми статусами и `recommendationDiagnostics`. Последнее различает available, needs_career_goal, target_reached, no_eligible_events; содержит причины исключения кандидатов и формулу readiness. Отсутствие рекомендаций не заменяется выдуманным событием. Расчёт, ранжирование и public explanationSource сохранены.

Сотрудник добровольно завершает собственную активность; HR не может нажать completion за него. Нет публичного сравнения людей, штрафов за отказ или принудительной записи через рекомендации. Исторические обязательные мероприятия показываются отдельно и не рекомендуются как карьерные шаги.

## Внутренний контур и AI

Compose по умолчанию слушает только 127.0.0.1. Для корпоративного доступа нужен внутренний HTTPS reverse proxy, точный внешний APP_ORIGIN и ограничение доступности хоста. Простое скрытие ссылок в интерфейсе не используется как защита.

`AI_EXPLANATIONS_ENABLED=false` прекращает внешние AI-запросы даже при наличии ключа. При true и ключе OpenAI получает детерминированно подготовленные evidence; применять к реальным данным только после организационного разрешения. Профиль/completion всегда рассчитываются локально, provider ограничен 8 секундами, весь AI-route — 9.5 секунды плюс резерв на отправку. Ключ остаётся на сервере.

Остались корпоративный SSO, интерфейс сброса пароля/отзыва всех сессий, consent-based sharing, retention/deletion policy и управление секретами инфраструктуры. Не заявляем их как выполненные.

Технические основания: [Node.js scrypt](https://nodejs.org/api/crypto.html#cryptoscryptsyncpassword-salt-keylen-options), [OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html), [NextResponse cookies](https://nextjs.org/docs/app/api-reference/functions/next-response#cookies).
